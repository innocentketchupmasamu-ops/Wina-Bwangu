1. Introduction

Wina Bwangu operates mobile money and banking service booths across Lusaka District. Managing transactions, monitoring service limits, calculating revenue, and tracking financial performance manually can make it difficult to obtain accurate and timely business information. This project develops a web-based management system to support transaction recording, data management, and business performance monitoring.

The work covers requirements analysis and design, a client-side prototype, and a server-side application connected to PostgreSQL. The interface records transactions and presents business information through tables, performance indicators, and charts.

2. Development Tools and Technologies

HTML5, CSS3 and JavaScript create the client interface. HTML structures the pages, CSS controls layout and appearance, and JavaScript enables interaction, validation, data retrieval, and communication with the backend.

Python and FastAPI implement the server-side application. FastAPI exposes endpoints for retrieving information and submitting transactions. Server-side validation applies business rules before data is stored. Pydantic supports request validation and SQLAlchemy connects the application to the database.

PostgreSQL stores booths, services, their relationships, and transactions. Primary keys, foreign keys, and constraints help maintain data integrity. Visual Studio Code was used as the development environment and pgAdmin to inspect tables and run SQL queries. The browser communicates with FastAPI, which accesses PostgreSQL and returns results to the frontend.

3. System Design and Implementation

The system is organised around booths, services, and transactions. A booth-to-service relationship represents the fact that different booths offer different combinations of services.

The frontend provides navigation, transaction recording, transaction history, and a dashboard. Selecting a booth can display its location and restrict the available services to those assigned to that booth. Selecting a service displays its applicable revenue rate.

The backend validates submitted details, calculates financial values, and stores valid transactions. Transaction identifiers use the WB format. Dashboard information is retrieved from transaction data rather than fixed figures embedded in the webpage.

The supplied Appendix 1 dataset contains 308 records, numbered WB0000001 through WB0000308. These records provide the basis for the performance analysis.

4. Results and Implications of System Outputs

Analysis of the supplied dataset produced a total transaction amount of K650,733 and total revenue of K32,033.695. The combined monthly service limits amount to K740,000.

The difference between the combined limits and transaction amounts is K89,267 of unused capacity across the five services. This total does not mean that each individual service has substantial remaining capacity.

Airtel Money recorded K317,627 against a K350,000 limit, leaving K32,373. MTN Money recorded K138,182 against K160,000, leaving K21,818. Zamtel Money recorded K64,334 against K70,000, leaving K5,666. Zanaco recorded K51,441 against K80,000, leaving K28,559. FNB recorded K79,149 against K80,000, leaving only K851.

FNB is operating at approximately 98.94% of its monthly limit and therefore requires close monitoring. If its remaining capacity is exhausted, further transactions should be handled according to authorised company procedures.

Booth revenue and service-frequency tables can help management identify where revenue is generated and which services are used most often. This information can inform resource allocation, service planning, and monitoring of busy booths.

Tax indicators can help estimate potential obligations, but the applicable tax rate and calculation method must be confirmed. A 16% rate, where configured in the application, is an application assumption and is not specified as a rate in the case study.

5. Testing and Evaluation

Database queries were used to verify the supplied transaction count, total transaction amount, and total revenue. Backend testing also included checking database connectivity and transaction creation. All results reported for assessment should correspond to tests actually performed.

Functional tests should cover booth selection, location display, service availability, revenue-rate selection, and calculations. For example, a K1,000 Airtel Money transaction at a rate of 0.05 should generate K50 in revenue.

Validation tests should confirm that negative amounts, invalid booth or service identifiers, unavailable booth-service combinations, and transactions exceeding a service's remaining limit are rejected appropriately. Integration tests should confirm that transactions submitted through the frontend are saved in PostgreSQL and reflected in dashboard responses.

Regression tests should repeat previously successful tests after changes, particularly changes to transaction calculations, authentication, or database queries. Responsive tests should check usability on desktop and mobile-sized screens.

6. Recommended Operational Controls

Input validation should operate on both the frontend and backend, with backend validation remaining authoritative. Database constraints should prevent invalid relationships and duplicate transaction identifiers.

Authentication and role-based authorisation should restrict sensitive functions to approved personnel. Passwords should be securely hashed, and credentials should never be committed to the source repository.

Regular database backups should be made and restoration procedures tested. Transaction changes should be traceable, access to financial information should be limited, and alerts should notify management when a service approaches its monthly limit.

Financial calculations, including tax treatment and rounding, should be documented and reviewed against applicable business and regulatory requirements. Historical data should be preserved and corrections should be traceable.

7. Conclusion

The Wina Bwangu project demonstrates how a responsive web interface, a Python backend, and a relational database can support transaction management and business reporting. The dashboard converts transaction records into information that can help management monitor revenue, service utilisation, and remaining capacity.

Further production deployment would require comprehensive testing, verified tax rules, secure user management, reliable backups, and appropriate access controls.
